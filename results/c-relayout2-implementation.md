# Attempt 2 implementation notes (2026-11-16)

`ref/flat/p3holes.c` starts from the normalization, reverse index, and relocation code in `p3inc.c`, but retains every common allocation that fits its previous capacity/alignment and arena. A shrink retains capacity; deletion or growth beyond capacity releases the previous allocation. All frees precede allocations, in ascending unified ID. Free lists are address-ordered and coalescing, owned by each arena, including its overflow allocations. Allocate first-fit from that arena's holes, then its tail, then the bucket's shared spare tail. Alignment padding in overflow becomes an owning-arena hole. Other symbols never move. Zero-size existing symbols may retain zero-capacity addresses; newly allocated zero-size symbols reserve one alignment unit.

Initial A is compact within arenas, ordered as in attempt 1 (type-string/ID order in bucket 6; alignment/ID elsewhere), with exactly 64 B extra before alignment rounding. Each bucket additionally reserves a fixed 64 KiB shared extent, independent of either B input. Frozen section/generated anchors translate past the bucket spare. Initial reserved slack is 2,313,220 bytes total, 1,817,765 produced, against original image 109,486,380; total virtual check buffer 145,913,440. Unknown packages, exhausted shared extents, changed frozen-anchor membership, and unsupported huge alignments are not general production allocator support.

`verify` constructs a fresh allocator from A, scans the complete unified ID universe independently at every historical transition to derive replacements, applies the allocation rule, and compares exact addresses/capacities, tail cursors, ordered hole geometry, and bucket cursors. It copies and relocates every final symbol into a fresh zero image and compares every byte, then compares the separate offset table. The reference shares the allocation rule and primary relocation evaluator by design; `p3inc_check` separately evaluates raw input relocations and validates alignment/overlap/image bytes, and `check-p3holes-table.py` separately evaluates table order and offsets. The update cannot consume scratch target addresses: patch and copy read the maintained address map, and reference address caches are restored after checks.

Benchmark inputs precompute changed-ID lists; the update performs actual hole allocation/free, reverse-index mutation, clears, copies, relocation stores, and table writes. Both edits separately accumulate >=1 second per direction. Chain mode accumulates >=1 second total across its four sequential steps, avoiding an impractical number of deletion cycles merely to accumulate a second in the tiny addition. Three complete cycles are history-checked before timing. Timed repetition must end with the exact checkpoint image, addresses and capacities plus a hash of hole geometry/tail/spare state. A further full cycle checks every intermediate endpoint with full-history replay. This validates a stable repeated allocation history; setup and reference replay are outside timing.

The initial addition grows one common text symbol (moves one address), with 12 repatches and 755 changed image bytes. Its return retains the larger capacity, moving zero common addresses, with 5 repatches and 514 changed image bytes. The initial deletion moves zero common symbols, 45,336 repatches, 20,807,401 changed image bytes; return 82,848 repatches and 20,807,505 changed bytes. The bulk bytes clear deleted content and restore it; they no longer recopy/repatch moved live descriptors. Warm counters are explicitly printed separately because placement after a return is a history-dependent result.

The separate sorted table holds 32-bit offsets from the types anchor. Bucket 6 contains full descriptors, not those offsets; the table is additional experimental metadata, not a claim that the frozen runtime accepts this layout. Sorted membership is part of prepared input, as in the previous experiment. Only changes involving bucket 6 trigger table maintenance; actual offset values are emitted during the update and the removed suffix is zeroed. Deletion/return writes 133,044 bytes, addition writes zero. Counts include these stores but image `bytes_changed` excludes the separate table. `written` is clear + copy + relocation stores + table stores (repeated stores count), not cache traffic. Fragmentation reports hole count/bytes, unused arena tails, unused shared spare, and live allocations' retained unused capacity.

CLI: `p3holes A B seconds [B1]`; optional B1 runs A->B->A->B1->A. `P3INC_EXPORT` exports initial `a.addr/img/table`, first B `b.addr/img/table`, and `anchors`; chain mode also exports the active endpoint under pre-created `step1` through `step4` subdirectories (tag a for A, b for either B). `P3HOLES OK` and chain timings conclude a passing run.
